The first class

Agent safety and the sandbox, then team work for the rest of the period.

Why a boundary exists

Gemini Enterprise lives in a browser. It cannot reach a file on your machine. Antigravity runs on your laptop: it reads and writes your files, and it drives GitHub and the database. It can take those steps without asking you first. A tool that acts needs a boundary. A chat window does not.

The agent is constantly reading text nobody on your team wrote:

  • A README in a repository you cloned.
  • An issue or a comment someone else wrote.
  • A web page you pointed it at.
  • A data file you did not create.

None of that came from you, and all of it arrives as words the agent reads. Untrusted text can become instructions, and the agent cannot always tell the difference.

That is indirect prompt injection: instructions hidden inside content the agent reads, which it may follow as if you had typed them. You never see the instruction. You see the result. It is called indirect because the attacker never talks to you — they write something and wait for an agent to read it.

One documented case, read as a shape

In a published and patched advisory against another agentic editor, injected content caused the agent to write a configuration file, that file was then executed automatically, and the result was remote code execution on the developer's machine.

Read the shape, not the product:

  • Nothing was broken into. The agent did what it was told.
  • The instruction arrived in content, not from the user.
  • The damage came from a step that ran without a human.

That vendor patched that one. The shape it belongs to is not a bug that gets patched once.

And this is what is sitting on your laptop while you work:

  • SSH keys — your access to every repository you can push to.
  • Environment files — database passwords and API keys, in plain text.
  • Cloud tokens — signed-in sessions for services that hold real data.
  • Your coursework — every other course you are taking, on the same disk.

What the sandbox does

  • Sandboxed commands write only to project, temp and build-cache paths.
  • Anything not mounted is invisible from inside.
  • System directories such as /usr and /etc are read-only.
  • ~/.ssh and .env are blocked by name.
  • Network access is limited to approved domains.

Windows, said plainly. The Windows sandbox mechanism is not documented. Treat it as unverified. The macOS and Linux mechanisms are documented; do not assume Windows behaves the same way. If you are on Windows, verify more, not less.

The sandbox limits what a command can reach. It does not judge whether the instruction was a good idea.

The approval prompt is the feature

The prompt appears exactly when an action crosses the boundary. It is the one moment a person is in the loop. Clicking through it without reading is the whole defence, discarded. The modal is not friction in your way — it is the design working.

Approval fatigue is the real risk. The twentieth prompt of the morning gets the same click as the first, and by then you are approving a category rather than an action. Slow down when the prompt names something outside your project.

The agent acting without asking does not move ownership. You still own what shipped. That is why every pull request declares AI use: the tool, what it produced, and what you changed — or AI-Assisted: none, which is equally legitimate. Not declaring is the offence. The declaration is not a confession; it is the record of who checked what, and it is the only one that exists.

In the room: three checks on your own machine

Verify the boundary. Do not trust it.

  1. Write inside your workspace — expect it to succeed.
  2. Read something outside it — expect a refusal or a prompt.
  3. Trigger one crossing action — read the modal, and describe what it says.

Then report what you saw:

  • A refusal you expected and did not get is a finding. Tell the instructor.
  • A refusal you did not expect is normal. Read the path in the message.
  • Do not disable the sandbox to make an error go away.

Nobody is graded on their machine misbehaving. You are on record for what you shipped, not for what your laptop did during a check.

The second class

The Phase 2 delivery. There are no slides for this session and it is not a queue of private meetings: all teams are in the room, each team presents, and the rest of the class is the audience and the question pool. You take questions from the room, and you ask them. Every delivery is presented from a public address.

Due this week

Phase 2 — stories, contracts, the split, the environment, and your token plan. 10 marks. The delivery contains:

  • A backlog at or above the floor, ordered, with acceptance criteria.
  • Interface contracts for every boundary between members.
  • The split — who holds which named stories this sprint.
  • The schema, with keys marked and row-level security enabled on every table.
  • A verified environment, working for every member.
  • The token plan, and the first ledger entry.

The phase is tagged in the repository at its due date, and the tag is what gets graded — not a submitted document and not a slide deck. See your repository for the tag names and the rules, and deliverables for the date and the floor.
