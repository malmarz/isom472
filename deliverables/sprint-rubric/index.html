Sprint rubric

How Phases 3, 4, 5 and the Phase 6 sprint are read — every coding sprint.

ISOM 472 › Deliverables › Sprint rubric

The marks are not for how many features you ship. They are for how you build: knowing who the work is for, agreeing it with them, and showing the value it creates. A small system the client asked for is worth more than a large one they did not.

1. How a rubric is read #

One rubric for every team. Each row is read at one of three levels from the repository at the tag: not there, there with gaps, meets. “Meets” is written so that you can check it yourself before the tag. The ledger row is binary. Workflow slips are warnings, recorded privately, not deductions in this phase. Marks are private: a team channel gets the team's levels and its warnings count; your own rows reach you directly.

2. What we read, and when #

The same rubric after every coding sprint. Phase 3 is read at the phase-3 tag at 8:00 am on Mon 26 Oct 2026, the delivery day; later dates are in the table of the six phases, and any change is announced in General. You may move the tag before the cutoff. Work after the tag is not marked, but it is still required. With no tag, we read main as it stood at the cutoff.

Each row is made of the requirements written in it. Every requirement counts: one you leave out costs part of the row, even when the rest is done. Using AI is fine for everything, reviews included, but a review must say what you ran, what you read and what you clicked.

4. New in Phase 3 #

  • Building is now marked. “2 stories per member” means the stories you build — you are the Assignee — not the stories you wrote.
  • Every phase, 2 stories each. Each member delivers 2 stories as Assignee in every phase. Stories you finished before Phase 3 count toward Phase 3 only. Phase 4, Phase 5 and the Phase 6 sprint each need 2 new stories per member, delivered within that phase.
  • Security Advisor. Your instructor will go through the Supabase Security Advisor with each team as a consultation. It is not graded.
  • Three things from Phase 2 are now required, inside rows C and D: db/schema.sql runs on an empty Supabase project, with a policy on every table that names who reads and who writes (an allow-everything policy does not count, and do not ALTER a policy the file never created — the file will not run); every story that takes input has a missing-value and a wrong-value criterion that names the message the user sees; and the split is fair.

Adding a story outside your proposal: see the four scope-change steps.

6. Workflow slips #

Workflow slips — merging your own work, approving without reviewing, pushing straight to main, signing for a teammate — are recorded as warnings, not deductions. Each warning is explained with what went wrong because of it, and we discuss it with the team or the class as a lesson.
