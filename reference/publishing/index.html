Publishing from your repository

Move work into the team repository, then publish the proposal at its own address.

ISOM 472 › Reference › Publishing

This page has two parts. The first is the everyday loop for moving a change from your laptop into the team repository with GitHub Desktop: clone, change, commit, push. The second is a one-time setup that gives your team's proposal a public web address.

Part 1 — The GitHub Desktop loop

This assumes GitHub Desktop is already installed and signed in to your own GitHub account, from the setup guide, and that the instructor has already created your team's repository. Every student uses this same loop for everything the team produces — code, the prototype, the ledger, notes — all in the same repository.

Clone the team repository

  1. Open GitHub Desktop.
  2. Open the File menu — on Windows this is inside the GitHub Desktop window itself; on macOS it is in the menu bar at the top of the screen — and choose Clone repository…
  3. Select the GitHub.com tab and find your team's repository in the list.
  4. Choose a folder on your laptop for the local path, then click Clone.

You should see GitHub Desktop finish downloading and show your team's repository, with its files visible in the folder you chose.

Change a file

  1. In GitHub Desktop, open the Repository menu and choose Show in Explorer (Windows) or Show in Finder (macOS). This opens the cloned folder.
  2. Open any file in that folder, make a small change, and save it.

You should see the file saved with your change, still inside the folder GitHub Desktop cloned — not a copy saved somewhere else.

See the change in GitHub Desktop

  1. Switch back to GitHub Desktop.
  2. Open the Changes tab on the left.

You should see the file you edited listed under Changes, checked, with the changed lines shown in the panel on the right.

Commit

  1. In the box at the bottom left, type a one-line summary of what you changed — for example Add literature review section, not update or changes.
  2. Click Commit to main.

You should see the Changes list empty out, and your commit appear at the top of the History tab.

Full rules for what a commit message should contain are on the repository page — read them before your team's first real commit.

Push

  1. Click Push origin near the top of the GitHub Desktop window.

You should see the button change to Fetch origin. Your commit is now on GitHub, and your teammates can see it.

When it goes wrong

What actually goes wrong, and what to do:

  • You pushed to the wrong place. Check the repository name at the top of the GitHub Desktop window before you push — it is easy to have more than one repository cloned and lose track of which one is open.
  • The button says "Fetch origin" instead of "Push origin". A teammate pushed before you did. Click Fetch origin, then Pull origin to bring their commit down, and only then push yours.
  • Your change is not listed under Changes. You edited a copy of the file saved somewhere else — check that the file you opened was inside the folder GitHub Desktop cloned, not a duplicate on the Desktop or in Downloads.

Part 2 — Giving the proposal a public address

The proposal is delivered twice. docs/proposal.md in the repository is the document that gets graded. The same content, published as a page from your team's own repository, is delivered a second time — presented from its live address and checked only as reachable, not judged on how it looks.

Turn on GitHub Pages for the team repository

  1. On github.com, open the team repository.
  2. Click Settings, then Pages in the left sidebar.
  3. Under Build and deployment, set Source to Deploy from a branch.
  4. Set Branch to main and the folder to / (root).
  5. Click Save.

You should see the Source section show Deploy from a branch, main, and / (root) — the settings you just chose, saved.

Set this once and never change it. The repository's bare address is reserved for the team's running system later in the course, which is why the proposal page sits under /docs/.

Create docs/index.html

In the team's folder on your laptop, open the docs folder and create a file named index.html inside it. Put your proposal content in it. Start from this skeleton and replace the text with your eight proposal sections. It is not graded on how it looks — no stylesheet or script is needed. 

<!DOCTYPE html>
<html lang="en">
<head>
<meta charset="utf-8">
<title>Team Name — Project Proposal</title>
</head>
<body>

<h1>Team Name — Project Proposal</h1>

<p>Replace this paragraph with your first proposal section.</p>

<p>Replace this paragraph with your next proposal section, and keep
adding headings and paragraphs until all eight sections are here.</p>

</body>
</html>

You should see the file open correctly if you double-click it on your own laptop before committing it — a heading and your text, unstyled.

Commit and push it

Use the same loop from Part 1: the file is listed under Changes in GitHub Desktop, write a one-line commit summary, click Commit to main, then click Push origin.

You should see the History tab show your commit, and the button change to Fetch origin, same as any other push.

Read the live address

  1. Wait a minute or two — the first build takes time.
  2. Reload the Settings › Pages screen.
  3. Read the address shown there and add docs/ to the end: https://<owner>.github.io/<repo>/docs/

You should see a live address listed on the Pages settings screen.

Check it

  1. Open https://<owner>.github.io/<repo>/docs/ in a browser.
  2. Check it again from a phone, off the campus network — on phone data, not KU wifi.

You should see your proposal's content load at that address, from a network with no connection to the university at all. "Reachable" means reachable by anyone.

When it goes wrong

What actually goes wrong, and what to do:

  • The address returns a 404 for the first minute or two after the first push. That is normal. Wait, then reload.
  • The folder was left at /docs instead of / (root). The proposal page then lands at the bare repository address instead of under /docs/. Go back to Settings › Pages and set the folder to / (root).
  • The file is named something other than index.html. Rename it — GitHub Pages only serves index.html automatically.
  • The address still shows nothing new. The change was committed but never pushed — check that GitHub Desktop says Fetch origin, not Push origin, before you assume it is live.

The team repository is public, so anything committed to it can be read by anyone. Never put a password, a key, or a client's private data in it.

"Delivered" means both things: the file in the repository, and the page reachable at its address. One without the other is not delivered.
